# 代码审查设计

## 目标

对 STM32G4-Balance 全项目进行预防性深度审查，产出结构化审查报告供用户批注决策。

## 审查参数

| 参数 | 值 |
|------|-----|
| 范围 | 全项目（Core/Src + Core/Inc + 外设驱动 + ISR） |
| 严苛度 | 最高：安全 + 控制理论 + 并发时序 + 代码质量 |
| 产出 | `docs/CODE_REVIEW.md`（含批注区） |
| 基准分支 | `balance_pid` |

## 执行流程

### Phase 1: 影响分析（GitNexus 驱动）
- 近期改动波及范围
- 高风险符号上下游行依赖
- 热区 Top-N 符号定位

### Phase 2: 分类深度审查
按四个维度逐项检查：

**安全（S1-S9）**：NaN/Inf 传播、传感器故障降级、保护机制完备、ISR 安全、栈溢出、初始化顺序、IWDG 喂狗覆盖、IWDG 周期合理性、IWDG 启动时机

**控制理论（C1-C6）**：误差符号一致性、离散化精度、级联带宽比、EMA/滤波器参数、积分限幅一致性、单位转换

**并发时序（T1-T7）**：参数竞态、循环超时级联、ADC ISR 抢占窗口、定时器触发抖动、编码器快照一致性、BT/CLI 并发写入、IWDG vs RTOS 调度时序

**代码质量（Q1-Q5）**：魔法数、死代码/冗余、错误处理缺口、文档同步、架构边界

### Phase 3: 执行流交叉验证
对发现的问题沿 GitNexus 执行流验证实际运行时影响

### Phase 4: 产出报告
`docs/CODE_REVIEW.md`，每项问题附带批注区：

```
> **批注区**
> - [ ] 修复  [ ] 不修复  [ ] 推迟
> 说明：_____________
```

另含：看门狗专项分析、架构时序专项分析、正面发现
